# L1 vs L2 cache

> L1 = closest, fastest, in-process. L2 = distributed, shared across instances.

## L1 — in-process cache

- Lives **inside the process** (JVM heap).
- Ultra fast (nanoseconds).
- **Not shared** between instances.
- Lost on restart.

Tools: `Caffeine`, `Guava Cache`, Hibernate Session cache.

## L2 — distributed cache

- **External** to the process (separate service).
- Slower than L1 (milliseconds — but still much faster than the DB).
- **Shared** across instances.
- Persists (depending on configuration).

Tools: **Redis**, Memcached, Hazelcast.

## Trade-offs

| | L1 | L2 |
|---|---|---|
| Speed | ⚡ ns | ms |
| Shared | ❌ | ✅ |
| Survives restart | ❌ | ✅ (Redis with persistence) |
| Consistency between pods | ❌ (each pod its own) | ✅ |
| Memory pressure | Per-pod | Centralized |

## Other contexts (so you don't get tripped up)

- **Hibernate L1/L2** — L1 is the Session cache (always on), L2 is an optional shared cache (Ehcache, Hazelcast).
- **CPU L1/L2** — hardware caches on the chip; not the same conversation.
