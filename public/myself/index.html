Follow-ups técnicos

"What do you mean by multi-threaded processing?"

A lot of the slowness there came from independent lookups being fetched sequentially, when they didn't actually depend on each other — fetch A, then B, then C, then assemble. I refactored that path to fire those calls in parallel using CompletableFuture over a dedicated virtual-thread executor — Java 21 gives you virtual threads, which are cheap to spin up and unmount automatically when they block on I/O, so you get real parallelism without exhausting OS threads. That turned a request that used to cost the sum of four or five sequential calls into just the cost of the slowest one running alone.

Si insisten en cuidados: no compartir estado mutable entre branches paralelas, acotar el executor (el pool de conexiones a DB es finito), y preservar el traceId a través del boundary async.

"What do you mean by layered caching?"

I used a two-layer approach — an L1 cache living inside the JVM process for the hottest, smallest lookups, and Redis as an L2 layer shared across all instances. L1 is nanosecond-fast but not shared and gets wiped on restart; Redis is a bit slower, milliseconds, but still far faster than hitting Oracle, and it stays consistent across every pod. The real work was deciding what belongs in which layer, and getting invalidation right — writes invalidate explicitly instead of just waiting on a TTL, so one instance doesn't serve stale data while another already has the update.
